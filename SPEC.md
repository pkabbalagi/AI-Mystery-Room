# AI Mystery Room — Project Specification

## 1. Project Overview

AI Mystery Room is an AI-powered web application where users create and solve interactive detective mysteries generated by Google Gemini.

The user provides a mystery premise and selects a difficulty level. The backend uses Gemini to generate a complete mystery containing a story, suspects, clues, hints, a culprit, and a logical explanation. The player investigates clues, optionally requests hints, accuses a suspect, and receives a verdict and score.

### Problem Statement

Traditional mystery games are static and limited to pre-written cases. AI Mystery Room allows players to generate unlimited original mysteries from their own premises while maintaining a structured investigation, clue-discovery, hint, accusation, and scoring experience.

### Target Users

- Students and casual gamers who enjoy detective puzzles.
- Users who want short, replayable AI-generated mystery games.
- Developers evaluating an AI-powered full-stack application.

### Expected User Experience

The application should feel like a detective investigation room:

- The user can quickly create a mystery from a simple premise.
- The mystery should be readable, engaging, and logically solvable.
- Suspects, clues, and hints should be clearly presented.
- The player should not see the culprit or solution before making an accusation.
- The result screen should clearly explain whether the accusation was correct and why.

2. Users can select Easy, Medium, or Hard difficulty.
3. Gemini generates a mystery with suspects, clues, hints, culprit, and solution.
4. The backend validates the AI response before saving it.
5. Players can view the mystery story and suspect cards.

## 4. User Flow

1. User opens the website.
2. User reads the project introduction on the Home page.
3. User clicks **Start Investigation**.
4. User enters a mystery premise, such as “A valuable painting disappears from a school art room.”
5. User selects a difficulty level: Easy, Medium, or Hard.
6. User clicks **Generate Mystery**.
7. Backend sends the premise and difficulty to Gemini.
8. Gemini returns structured mystery data.
9. Backend validates and saves the mystery in MongoDB.
10. Frontend redirects the user to the Investigation Room.
11. User reads the story and reviews suspects.
12. User discovers clues.
13. User may request hints.
14. User selects a suspect and submits an accusation.
15. Backend checks whether the accusation is correct.
16. Backend calculates and stores the score.
17. Frontend displays the result, culprit, explanation, and score.
18. User can click **Start New Mystery**.

|---|---:|---:|---:|---:|
| Easy | 3 | 5 | 2 | 100 |
| Medium | 4 | 7 | 3 | 150 |
| Hard | 5 | 9 | 3 | 200 |

## 6. Scoring Rules

Scoring must be calculated only on the backend.

- Correct accusation base score:
  - Easy: 100 points
  - Medium: 150 points
  - Hard: 200 points
- Each discovered clue: +5 points
- Each hint used: -10 points
- Wrong accusation: 0 points
- Minimum possible score: 0 points

### Score Formula

For a correct accusation:

```text
finalScore = baseScore + (discoveredClues * 5) - (hintsUsed * 10)
```

If the calculated score is below 0, set it to 0.

For an incorrect accusation:

```text
finalScore = 0
```

## 8. API Design

Base URL:

```text
/api
```

All responses should use JSON.

### Success Response Format

```json
{
  "success": true,
  "data": {}
}
```

### Error Response Format

```json
{
  "success": false,
  "error": "Descriptive error message"
}
```

### POST /api/cases

Generates a new mystery.

Request:

```json
{
  "premise": "A valuable painting disappears from a school art room",
  "difficulty": "medium"
}
```

Validation:

- `premise` is required.
- `premise` must be between 10 and 500 characters.
- `difficulty` must be one of `easy`, `medium`, or `hard`.

Response:

```json
{
  "success": true,
  "data": {
    "caseId": "64f1a2b3c4d5e6f7a8b9c0d1",
    "title": "The Missing Painting",
    "story": "During the annual art exhibition...",
    "difficulty": "medium",
    "suspects": [],
    "clues": [],
    "hints": []
  }
}
```

The response must not include `culpritId` or `solution`.

### GET /api/cases/:id

Retrieves an active mystery.

Response:

```json
{
  "success": true,
  "data": {
    "caseId": "64f1a2b3c4d5e6f7a8b9c0d1",
    "title": "The Missing Painting",
    "story": "...",
    "difficulty": "medium",
    "suspects": [],
    "clues": [],
    "hints": [],
    "discoveredClues": [],
    "hintsUsed": 0,
    "status": "active"
  }
}
```

Rules:

- If the case does not exist, return 404.
- If the case is solved, return the completed result data.
- Do not expose `culpritId` or `solution` while status is `active`.

### POST /api/cases/:id/clues/:clueId/discover

Marks a clue as discovered.

Request:

```json
{}
```

Response:

```json
{
  "success": true,
  "data": {
    "clueId": "c1",
    "title": "Torn Canvas Corner",
    "description": "A piece of canvas was found near the storage room.",
    "discovered": true
  }
}
```

Validation:

- Case must exist.
- Clue must exist.
- Clue must not already be discovered.
- Case must not already be solved.

### POST /api/cases/:id/hints

Reveals the next available hint.

Request:

```json
{}
```

Response:

```json
{
  "success": true,
  "data": {
    "hintId": "h1",
    "text": "Check who had access to the art storage room.",
    "hintsUsed": 1
  }
}
```

Validation:

- Case must exist.
- Case must not be solved.
- There must be an unused hint available.

### POST /api/cases/:id/accuse

Submits the player’s accusation.

Request:

```json
{
  "suspectId": "s2"
}
```

Validation:

- Case must exist.
- Case must not already be solved.
- `suspectId` must match one of the case suspects.

Response:

```json
{
  "success": true,
  "data": {
    "correct": true,
    "culpritId": "s2",
    "culpritName": "Mr. Ravi",
    "solution": "Mr. Ravi hid the painting behind the storage cabinets...",
    "score": 160,
    "discoveredClues": 4,
    "hintsUsed": 2
  }
}
```

### GET /api/cases/:id/result

Retrieves the completed result.

Response:

```json
{
  "success": true,
  "data": {
    "caseId": "64f1a2b3c4d5e6f7a8b9c0d1",
    "title": "The Missing Painting",
    "accusation": {
      "suspectId": "s2",
      "suspectName": "Mr. Ravi"
    },
    "correct": true,
    "culpritId": "s2",
    "culpritName": "Mr. Ravi",
    "solution": "Mr. Ravi hid the painting behind the storage cabinets...",
    "score": 160,
    "discoveredClues": 4,
    "hintsUsed": 2,
    "status": "solved"
  }
}
```

Validation:

- Case must exist.
- Result can be retrieved only after an accusation has been submitted.

## 9. Database Design

Collection name:

```text
cases
```

### Case Schema

```js
{
  title: String,
  story: String,
  difficulty: String,
  suspects: [
    {
      id: String,
      name: String,
      description: String
    }
  ],
  clues: [
    {
      id: String,
      title: String,
      description: String,
      discovered: Boolean
    }
  ],
  hints: [
    {
      id: String,
      text: String,
      used: Boolean
    }
  ],
  culpritId: String,
  solution: String,
  accusation: {
    suspectId: String,
    suspectName: String
  },
  score: Number,
  status: String
}
```

### Field Rules

- `difficulty`: `easy`, `medium`, or `hard`
- `status`: `active` or `solved`
- `culpritId`: Must match one suspect ID
- `discovered`: `false` by default
- `used`: `false` by default
- `score`: `null` until accusation is submitted

## 10. Gemini Integration

The backend must call Gemini with a structured prompt and request JSON output.

### Required Gemini Output Format

```json
{
  "title": "string",
  "story": "string",
  "suspects": [
    {
      "id": "string",
      "name": "string",
      "description": "string"
    }
  ],
  "clues": [
    {
      "id": "string",
      "title": "string",
      "description": "string"
    }
  ],
  "hints": [
    {
      "id": "string",
      "text": "string"
    }
  ],
  "culpritId": "string",
  "solution": "string"
}
```

### Gemini Prompt Requirements

The prompt must instruct Gemini to:

- Create an original mystery based on the user premise.
- Use the exact number of suspects, clues, and hints for the selected difficulty.
- Make the culprit logically identifiable from the clues.
- Avoid revealing the culprit directly in the story.
- Ensure every clue supports the final solution.
- Return valid JSON only.
- Use unique IDs for suspects, clues, and hints.

### Validation Rules

Before saving, the backend must validate that:

- `title` and `story` are non-empty strings.
- The number of suspects, clues, and hints matches the selected difficulty.
- Every suspect has a unique ID, name, and description.
- Every clue has a unique ID, title, and description.
- Every hint has a unique ID and text.
- `culpritId` matches one of the suspect IDs.
- `solution` is a non-empty explanation.
- The generated JSON matches the expected Zod schema.

If validation fails, the backend should retry once. If it fails again, return a user-friendly error.

## 11. Error Handling

The application must handle:

- Empty or invalid premise.
- Invalid difficulty.
- Gemini API failure.
- Invalid Gemini JSON response.
- MongoDB connection failure.
- Invalid case ID.
- Discovery of an already-discovered clue.
- Requesting more hints than available.
- Accusing an invalid suspect.
- Accusing after the case is already solved.
- Network failures in the frontend.

Each error should show a clear, friendly message in the UI.

- Easy mysteries contain 3 suspects, 5 clues, and 2 hints.

- Players can discover clues.
